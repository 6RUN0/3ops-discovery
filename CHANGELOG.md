this file. Russian original: [CHANGELOG.ru.md](CHANGELOG.ru.md).

## 0.3.0 -- Draft

The contract is no longer tied to one agent: sections 1-13 state requirements any implementation can meet, and Alloy becomes the reference implementation. For a consumer of `0.2.0` labels, defaults, series and log fields do not change, except for the two reference fixes and the one known limitation at the end of this entry. The value of `ru.3ops.discovery.version` stays `"0.2"`: no label changed its meaning (section [7](docs/manifest.md#7-contract-versioning)).

- Sections 1-13 name no implementation. The mechanics of the reference (Alloy components, overlay files, relabel rules) moved to [14.4.4](docs/manifest.md#1444-how-the-reference-fulfils-the-contract), ordered by contract section; that list adds no requirements. The static gate `tests/static/test_manifest_neutrality.py` counts implementation mentions per section and allows them only in sections 1 and 14 (the `MANIFEST_IMPLEMENTATION_MENTIONS` table). The gate sees agent and component names; it does not count generic words such as "reference".
- Section [14](docs/manifest.md#14-implementations) "Implementations" replaces "Reference implementation": a registry of implementations with their domains, the duties of an implementation for each of its domains, and the rule "one collector per domain per host". Two collectors of one domain on a host produce duplicate series and lines the storage cannot tell from real data, so such a deployment is an error; the symptom is series or streams that differ only in `collector` or `host`.
- The explanatory prose of the former section 14 about how the reference configuration is built (file order, profile component pairs, multiple container networks, stores, collector state) moved to [`implementations/alloy/README.md`](implementations/alloy/README.md); links in the earlier entries point at its sections.
- The `collector` label carries the implementation name ([6.1](docs/manifest.md#61-labels-added-by-the-implementation)); for the reference it is still `alloy`.
- The new environment parameter `RU_3OPS_DISCOVERY_HOSTNAME` ([14.1](docs/manifest.md#141-environment-parameters)) sets the value of the `host` label. An unset or empty parameter yields the collector hostname, as in `0.2.0`. In the host-metrics and container-metrics domains the parameter does not set `instance`: there it is the collector hostname, and it equals `host` only while the parameter is unset or empty.
- Section [14.2](docs/manifest.md#142-output-protocols-and-stores) "Output protocols and stores" replaces "Backends". Metrics go over the remote_write protocol to any compatible store. For logs the contract fixes the result in the store (the fields of sections 6.2 and 8.3), not the protocol. VictoriaLogs without the `-loki.disableMessageParsing` flag adds fields from a JSON line and loses the original line in `_msg`. The delivery guarantee is no stronger than at-least-once: a collector restart may resend log history and lose unsent metrics.
- The series catalog ([14.3](docs/manifest.md#143-series-catalog), [`docs/series/`](docs/series/)): one `<domain>.yaml` file per domain; a cell lists the series every implementation of the domain must emit and the identity labels of each series, and for database also the series the profile switches off. The catalog is a lower bound and pins names only: a change of unit or series type under the same name is invisible to it. It is snapshotted from the e2e stack of the reference at the pinned version and rebuilt on every pin change. The e2e gate `tests/e2e/test_series_parity.py` checks that the reference serves the catalog; `tests/e2e/test_log_fields_parity.py` checks that the non-indexed fields of every log profile are exactly those of the 8.3 table, and the fields the store adds by itself are listed per store in `asymmetries.STORE_DERIVED_LOG_FIELDS`.
- The host domains host-metrics, container-metrics and host-logs joined section [10](docs/manifest.md#10-domains): they are not driven by labels, are off by default and require deployment privileges. In the reference they are the existing opt-in files 070, 075 and 080.
- [10.3.1](docs/manifest.md#1031-default-collection-policy): the norm for a container with `logs.enabled=false` is that its lines are not delivered to the store. An implementation may leave the stream of such a container unopened or read the stream and drop the lines before sending; the reference still leaves the stream unopened.
- The database profiles of [8.4](docs/manifest.md#84-database-profiles) are described by series families rather than by exporter collectors; the families were checked against the exporter sources.

- Wording clarifications. The delays of section [12](docs/manifest.md#12-lifecycle) are one `RU_3OPS_DISCOVERY_DOCKER_REFRESH_INTERVAL` interval plus processing time, not exactly one interval. The ban in [13.3](docs/manifest.md#133-docker-socket) covers obtaining container logs and metadata from the files of `/var/lib/docker`, so it does not contradict the host root mount of the opt-in host-metrics. The English translation of [10.3.6](docs/manifest.md#1036-examples) said `mixed-v1` "may" apply the parsers and lacked the rule that the branches are mutually exclusive and that `level=` is anchored to the line start or a space: a reader of the translation got a weaker contract; the paragraph is restored.
- Fixed in the reference: postgres `extended-v1` replaced the exporter's default collectors instead of adding to them, so it collected less than `standard-v1` (no database size, locks, `pg_stat_database`, bgwriter, WAL or replication series). It now keeps the default collectors plus the four extras ([8.4](docs/manifest.md#84-database-profiles)).
- Fixed in the reference: mongodb on `standard-v1` and `extended-v1` serves the full set from the first scrape of each exporter. mongodb_exporter v0.47.2 widens `collect_all` only after its first scrape, so the first scrape (and the 60 seconds after a container is discovered) returned only `mongodb_up`, the fcv series and `collector_scrape_time_ms`.
- Known limitation of the reference: for redis `basic-v1` equals `standard-v1` in series. In redis_exporter v1.86.0 (embedded in the pinned Alloy v1.21.2) the `redis_metrics_only` flag drops only `redis_exporter_build_info` from the exporter's internal registry, which Alloy does not serve (Alloy serves a same-named `redis_exporter_build_info` of its own, the integration build info, regardless of the flag), so choosing `basic-v1` does not reduce the collection volume. The comment in [`030_database.alloy`](implementations/alloy/base/030_database.alloy) claimed that `basic-v1` drops the exporter's own Go runtime metrics and is corrected; the profile stays in the allowlist.
- The reference moved to `implementations/alloy/`: `alloy/` became [`base/`](implementations/alloy/base/), `alloy-optional/` became [`optional/`](implementations/alloy/optional/), and the reference README moved next to them. The old paths `alloy/` and `alloy-optional/` no longer exist, so a deployment that mounts `alloy/` must change the path. `010_discovery.alloy` is split into `010_discovery-scrape.alloy` and `011_discovery-logs.alloy`, and `090_outputs.alloy` into `090_output-metrics.alloy` and `091_output-logs.alloy`. Component names and the extension points of [14.4.2](docs/manifest.md#1442-extension-points) are unchanged, so a user overlay needs no edit; a copy of an old `010_discovery.alloy` or `090_outputs.alloy` left next to the new files declares the same components twice and Alloy rejects the directory.
- Deployment by domain: the file tables of [14.4](docs/manifest.md#144-reference-implementation-alloy) and [14.4.3](docs/manifest.md#1443-optional-files) carry a `Domains` column, and the union of the files of the chosen domains is a complete configuration (`tools/materialize.py`, [`implementations/alloy/README.md`](implementations/alloy/README.md)). The `--stability.level=experimental` flag is needed exactly when the set includes `database`, the only domain that uses `foreach`; a set without it loads without the flag. The default set and the full set are unchanged.
- Second implementation of the `metrics` domain: [`implementations/vmagent/`](implementations/vmagent/README.md) on VictoriaMetrics vmagent v1.154.1, registered in the table of section [14](docs/manifest.md#14-implementations) for `metrics` and `ipmi`; its series carry `collector="vmagent"`. One `scrape.yml` carries the relabel rules of the reference in their order, and `entrypoint.sh` applies the 14.1 defaults, because vmagent keeps an unset `%{NAME}` placeholder as literal text and starts anyway. A domain on a host has one collector, so with vmagent Alloy no longer serves `metrics` and `ipmi` (an ipmi exporter is scraped as a metrics target): the Alloy directory is the union of the files of the domains Alloy still serves ([14.4](docs/manifest.md#144-reference-implementation-alloy)). Files shared with other domains stay, so for the default set only `020_metrics.alloy` leaves the directory.
- Gates of the second implementation: `uv run nox -s vmagent_check` (part of the default `uv run nox`) parses the configuration with `-dryRun` in the pinned image, once with no environment and once with the e2e values; `uv run nox -s e2e_vmagent` and `uv run nox -s e2e_vmagent_victoria` run the contract subset of e2e (`-m "not alloy_internals"`) with vmagent as the metrics collector, on Prometheus + Loki and on VictoriaMetrics + VictoriaLogs. `tests/e2e/test_series_parity.py` judges each catalog cell against the collector of the cell's domain, so the `metrics/scrape` cell is checked on what vmagent delivers, and a gap row excuses only the series of its own implementation.
- How vmagent differs from the reference in mechanics; the contract behaviour is the same. `docker_sd_configs` has no `refresh_interval`, so `RU_3OPS_DISCOVERY_DOCKER_REFRESH_INTERVAL` becomes the `-promscrape.dockerSDCheckInterval` flag, which applies to every Docker discovery of the process. vmagent dials only `unix://` and `http(s)://`, so the entrypoint rewrites Docker's `tcp://host:port` to `http://host:port`; a TLS endpoint is given as `https://`. vmagent sends the discovery `filters` to `GET /networks` as well, so the `__meta_docker_network_*` labels other than `__meta_docker_network_ip` are absent; the rules read only the IP, so targets do not change (`asymmetries.DISCOVERY_META_LABELS_ABSENT`).
- Section [14](docs/manifest.md#14-implementations): `tests/static/asymmetries.py` lists the divergences of every implementation, not only of the reference. A row about an implementation other than the reference names that implementation and a domain from its registry row; `tests/static/test_implementation_gaps.py` checks this.
- Second implementation of the `logs` domain: [`implementations/vector/`](implementations/vector/README.md) on Vector 0.60.0, registered in the table of section [14](docs/manifest.md#14-implementations); its streams carry `collector="vector"`. One `vector.yaml` reproduces the log profiles of the reference (opt-out, stream labels from Docker metadata only, the 8.3 structured metadata fields, multiline for the stacktrace profiles, the `raw-v1` fallback), and `entrypoint.sh` applies the 14.1 defaults and splits `RU_3OPS_DISCOVERY_LOKI_PUSH_URL` into the sink address. A deployment that runs it leaves `011_discovery-logs.alloy`, `040_logs.alloy` and `050_log-profiles.alloy` out of the Alloy directory, and `091_output-logs.alloy` too unless Alloy serves `otel` or `host-logs`; one domain on a host has one collector.
- Gates of the logs implementation: `uv run nox -s vector_check` (part of the default `uv run nox`) validates the configuration in the pinned image, once with no environment and once with the e2e values; `uv run nox -s e2e_vector` and `uv run nox -s e2e_vector_victoria` run the contract subset of e2e with Vector as the logs collector, on Prometheus + Loki and on VictoriaMetrics + VictoriaLogs. The axis is `RU_3OPS_DISCOVERY_E2E_LOGS_IMPL`, independent of the metrics axis.
- How Vector differs from the reference, listed in `asymmetries.LOGS_IMPLEMENTATION_GAPS`: labels, fields and profiles are the same; two contract items are not met. Item 4 of [10.3.4](docs/manifest.md#1034-unknown-profile) (the error metric) is not met, because VRL cannot increment a metric, and the warning of item 3 is rate-limited per call site, so a second container with an unknown profile within a minute is collected as `raw-v1` but not named. The at-least-once delivery of [14.2](docs/manifest.md#142-output-protocols-and-stores) is not met: `docker_logs` keeps no read positions, so lines written while Vector is down, or before it starts, are lost; the reference resumes. It excludes its own container when the container hostname is a prefix of the container ID (Docker's default), so Vector needs an explicit `hostname:` to collect its own logs. `RU_3OPS_DISCOVERY_DOCKER_REFRESH_INTERVAL` is not read, because `docker_logs` follows the Docker event stream. A logfmt line over 64 KiB and a lone `\ud800` escape parse differently.
- Fixed in the reference: the OTLP path [`060_otel.alloy`](implementations/alloy/optional/060_otel.alloy) sets `host` from `RU_3OPS_DISCOVERY_HOSTNAME` and `collector="alloy"` on its series and streams and overwrites values sent by the sender. Without them OTLP series and logs could not be tied to a machine and a collector, and the duplicates of two collectors with otel did not differ at all. OTLP series gain two labels, so their identity in the store changes. The [10.5](docs/manifest.md#105-domain-otel) exemption covers only `environment`/`team`/`container`; 060 is no longer exempt from the provenance gate (`asymmetries.NOT_SERIES_PATHS`), and [14.4.4](docs/manifest.md#1444-how-the-reference-fulfils-the-contract) describes how the reference sets both labels.
- The remaining traces of the reference were removed from sections 1-13: the user `alloy_monitor` in the examples of sections [9](docs/manifest.md#9-secret-contract) and [10.2.2](docs/manifest.md#1022-postgresql-example) became `monitor`, and the "scrape pair with `tls_config`" of [10.1.1](docs/manifest.md#1011-labels) and the path of the validator `tools/snmp_fixtures.py` in [10.6.1](docs/manifest.md#1061-snmp-auth) moved to 14.4.4. The neutrality gate counts these tokens too: `alloy_*`, `tls_config`, `tools/`, "scrape pair".
- Known limitation of vmagent: it accepts pushed data without authentication on its HTTP listen port (`8429` by default): remote_write, `/api/v1/import`, InfluxDB, OTLP. A neighbour with access to the port writes series with any `container`, `host` and `collector`, and the guarantee of [13.5](docs/manifest.md#135-trust-in-labels) does not hold for them. The port is kept off networks shared with untrusted containers. The divergence is recorded in `asymmetries.METRICS_IMPLEMENTATION_GAPS`, in section [14](docs/manifest.md#14-implementations) and in the [vmagent README](implementations/vmagent/README.md#push-ingestion-port).
- vmagent README: the remote write address is set only by `RU_3OPS_DISCOVERY_REMOTE_WRITE_URL`. `-remoteWrite.url` is an array flag, so the same argument after `entrypoint.sh` adds a second destination instead of replacing the first.
- Fixed: the opt-out conformance check searched only streams labelled `app-silent`, so an implementation shipping opted-out lines under an empty or partial label set passed. `app-silent` writes a per-run marker, and the check also requires that a store-wide content search for it finds nothing, on Loki and on VictoriaLogs.
- Fixed: `docs/series/database.yaml` listed `pg_stat_database_blks_hit` for postgres `basic-v1` but not `extended-v1`, so a second implementation could drop it on the heavier profile and pass series parity. A static gate requires every heavier database profile cell to keep the series of the lighter one (ordering of [8.4](docs/manifest.md#84-database-profiles)).
- Fixed: the vmagent keep rules on `metrics.enabled`, `metrics.type`, `metrics.path` and `metrics.scheme` had no gate, and deleting any of them kept every check green. They are pinned to the reference regexes and must run before the target is addressed.
- Changed: the Vector unknown-log-profile warning is a JSON object with a constant `msg` and the `container` and `profile` values as escaped fields; a label value pasted into the text was unescaped input to the collector's log. An empty `logs.profile` falls back to `raw-v1` without a warning ([11](docs/manifest.md#11-validation-rules): empty equals absent).
- Fixed: e2e teardown and diagnostics (`compose logs`, `compose port`, `down -v`) could block on a hung Docker daemon and lose the diagnostics; each such call has a 120 s timeout.
- e2e: the OTLP checks assert `host` and `collector` on OTLP series and streams.
- `uv run nox -s ci_local` runs the GitHub workflows locally under act, one job at a time: `ci.yml` by default, the `e2e.yml` matrix with `-- e2e`. Not a gate.
- Section [14](docs/manifest.md#14-implementations): when several collectors serve the domains of a host, the deployment must give all of them one value of `RU_3OPS_DISCOVERY_HOSTNAME`. The default of [14.1](docs/manifest.md#141-environment-parameters) is unchanged; left unset, each domain reports the hostname of its own collector, and queries that join the domains of a machine by `host` no longer join them.
- Mixed deployment in e2e: `uv run nox -s e2e_mixed` and `uv run nox -s e2e_mixed_victoria` run the contract subset with vmagent for `metrics`, Vector for `logs` and Alloy for the other domains. On every e2e cell `tests/e2e/test_single_collector.py` checks that no series, target or stream of the stack is collected twice, and `tests/e2e/test_host_identity.py` that every domain reports one `host`. `alloy_check` validates the Alloy graphs that run next to vmagent, Vector or both (`beside-*` in `tools/materialize.py`).
- The release archive carries `tests/static/asymmetries.py`: the manifest links to it, and the static gate `tests/static/test_release.py` checks every relative link of the shipped manifests against the archive. The deployment README attaches the vmagent and Vector containers to the network of the store and docker-socket-proxy (`--network`), and its env-file example writes the host name itself: an env file is not run through a shell, so `$(hostname)` reached the collector as literal text.

## 0.2.0 -- Draft

- Docker stdout/stderr is collected by default for every container.
- `ru.3ops.discovery.logs.enabled=false` acts as the explicit opt-out.
- `ru.3ops.discovery.logs.profile` now names a predefined, versioned pipeline profile.
- Profiles of the form `json,logfmt,raw` are forbidden: a label is not a language for describing stages.
- `raw` is the implicit fallback of any profile whenever a parsing stage fails to read the line.
- Added the base profiles `raw-v1`, `generic-json-v1`, `generic-logfmt-v1`, `mixed-v1`.
- Added versioning rules for log pipelines.
- Free-form `interval`/`timeout` values in labels were replaced by the versioned allowlist profiles `metrics.profile`, `database.profile`, `blackbox.profile`.
- The version-in-the-name requirement was extended to all profiles, not just log profiles.
- The secret contract was generalized to the `snmp` and `ipmi` domains (per-domain secret file suffixes).
- Documented the exemption of the `logs` domain from the `ru.3ops.discovery.enabled` requirement.
- The reference Alloy configuration moved into the `alloy/` directory (files with numeric prefixes; the integration point with the backend is the outputs file, now split into [`090_output-metrics.alloy`](implementations/alloy/base/090_output-metrics.alloy) and [`091_output-logs.alloy`](implementations/alloy/base/091_output-logs.alloy)).
- Defined the `RU_3OPS_DISCOVERY_*` environment variable contract for deployment-specific parameters of the reference configuration.
- Fields extracted from log content go to structured metadata only, never to stream labels.
- The `secret-id` space is documented as a single trust domain of the host; binding a secret to a container identity is declared out of scope.
- Added section [13.5](docs/manifest.md#135-trust-in-labels) on the boundaries of trust in labels.
- The reference configuration implements the `path`/`scheme`/`profile` relabel validations and collapses the port fan-out for metrics and database.
- The database domain was extended to the types `mysql`/`mariadb`, `redis`, `mongodb`; the series of every exporter carry provenance labels (`environment`/`team`/`container`/`compose_*`/`collector`, plus synthesized `job`/`instance`).
- For redis the secret format is `host:port` in `.dsn` plus the password in a separate `<secret-id>.redispass` file (the `redis_addr` argument does not accept a secret).
- Added the multiline log profiles `python-stacktrace-v1` and `java-stacktrace-v1`: multiline tracebacks are glued into a single record.
- Introduced the `alloy-optional/` overlay directory and its first opt-in file [`060_otel.alloy`](implementations/alloy/optional/060_otel.alloy) (OTLP receiver: metrics into `prometheus.remote_write`, logs into `loki.write` through an allowlist processor).
- Documented the customization model: base extension points (section [14.4.2](docs/manifest.md#1442-extension-points)), optional files ([14.4.3](docs/manifest.md#1443-optional-files)), conventions against name collisions.
- Added tables of standard database ports ([10.2](docs/manifest.md#102-domain-database)) and of secret file formats per type ([9](docs/manifest.md#9-secret-contract)); recorded the provenance exemption of the OTLP path.
- Clarified that `database.type` denotes the wire protocol rather than the vendor: protocol-compatible builds (Percona Server for MySQL/MongoDB, XtraDB Cluster) are labelled with the base type `mysql`/`mongodb` without a type of their own.
- Added the optional host metrics file [`070_host-metrics.alloy`](implementations/alloy/optional/070_host-metrics.alloy) (`prometheus.exporter.unix`, `node_*` series); the rootfs/procfs/sysfs paths are parameterized by `RU_3OPS_DISCOVERY_HOST_ROOTFS_PATH`/`_PROCFS_PATH`/`_SYSFS_PATH`.
- Added the optional host logs file [`080_host-logs.alloy`](implementations/alloy/optional/080_host-logs.alloy) (`loki.source.journal` from the systemd journal into `loki.write`) with the static labels `host`/`collector`/`source`.
- Implemented the blackbox domain ([`035_blackbox.alloy`](implementations/alloy/base/035_blackbox.alloy)): HTTP probes driven by the `ru.3ops.discovery.blackbox.*` Docker labels through `prometheus.exporter.blackbox` (reference module `http_2xx`, profile `normal-v1`).
- The snmp domain ([8.5](docs/manifest.md#85-snmp-profiles)/[10.6](docs/manifest.md#106-domain-snmp)/[10.6.1](docs/manifest.md#1061-snmp-auth)/[14.4.3](docs/manifest.md#1443-optional-files)): a file-based device provider, the v2c/v3 (authPriv) auth model, the opt-in overlay [`037_snmp.alloy`](implementations/alloy/optional/037_snmp.alloy), static gates and e2e against a live Net-SNMP agent.
- Clarified the ipmi domain ([10.7](docs/manifest.md#107-domain-ipmi)): Alloy has no native IPMI component, so the domain is reformulated as a special case of `metrics` -- scraping the Prometheus endpoint of an external `ipmi_exporter`; the labels and the `.ipmi` secret suffix are kept (the contract semantics did not change).
- Added the optional per-container metrics file [`075_container-metrics.alloy`](implementations/alloy/optional/075_container-metrics.alloy) (`prometheus.exporter.cadvisor`, series `container_cpu_*`/`container_memory_*`/`container_network_*`): the Docker API through the socket proxy (reusing `RU_3OPS_DISCOVERY_DOCKER_HOST`), provenance per [6.1](docs/manifest.md#61-labels-added-by-the-implementation) built from allowlisted container labels (`name` becomes `container`, raw `container_label_*` are dropped), root cgroup statistics disabled; requires the host cgroup namespace (`cgroup: host`, a privileged overlay per [14.4.1](docs/manifest.md#1441-customization)).
- The reference configuration implements every base scrape profile of [8.2](docs/manifest.md#82-scrape-profiles) (`fast-v1`/`normal-v1`/`slow-v1`) for the metrics and blackbox domains: a shared relabel carries validation and provenance, a thin filter-plus-scrape pair per profile carries the routing; the names of profile components are derived from the full profile name.
- The blackbox domain gained the `tcp_connect` and `icmp` modules with per-component composition of the probe target (URL / `host:port` / bare host); probe series gained a `module` label; ICMP probes work without extra container privileges, and the way out for hardened environments is documented.
- Added the `tls_connect` module -- all four promised probe families (HTTP, TCP, ICMP, TLS) are now shipped by the reference; the module checks the TLS handshake and reports certificate expiry metrics, while trust chain verification is documented as an environment customization (`ca_file`).
- Implemented the database profiles of [8.4](docs/manifest.md#84-database-profiles) (`basic-v1`/`standard-v1`/`extended-v1`): a profile governs the collection volume of the exporter (the set of collectors) rather than the scrape cadence; `standard-v1` matches the exporter defaults, a value outside the allowlist drops the target (fail-closed); the mapping of profiles onto collectors per database type is documented in [8.4](docs/manifest.md#84-database-profiles).
- The snmp module allowlist ([10.6](docs/manifest.md#106-domain-snmp)) gained `system` (identity and uptime of agentless devices: `sysUpTime`, `sysName`); one device file entry means one module, so a device with several modules corresponds to several entries. Vendor modules (`cisco_device`, for example) stay outside the reference: the list is open and extending it is a property of the deployment.
- Behavioural review fixes of the reference: the `logs.enabled=false` opt-out excludes the container before `loki.source.docker` rather than line by line in the tailer; the mandatory `metrics.port`, `blackbox.port` and `metrics.job` are checked by a fail-closed presence keep -- a container with no exposed TCP ports no longer passes `keepequal` and is not scraped on port 80, and a missing `metrics.job` drops the target instead of substituting the name of the scrape component; an snmp entry without `name` takes its name from `address` instead of failing the whole exporter.
- The database domain: series carry `host`; series identity is `database.instance`, then the global `instance`, then `secret-id` (fallback); `database.name`/`user`/`sslmode` are declared inventory-only (the sole source of connection parameters is `.dsn`). Overlay [070](implementations/alloy/optional/070_host-metrics.alloy) adds the `host`/`collector` provenance to `node_*` series; snmp series carry a `device` label holding the device name.
- The `mixed-v1` profile: the JSON and logfmt stages were made mutually exclusive (a line cannot pass both parsers), and the stages gained `pipeline_name`.
